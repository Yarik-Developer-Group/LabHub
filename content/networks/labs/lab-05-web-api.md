## 1. Мета роботи

Розуміння клієнт-серверної архітектури вебу на практиці: що таке
веб-застосунок, ресурс, HTTP-метод і код відповіді. Усвідомлення,
**хто такий клієнт** (будь-хто, хто шле запит) і **хто такий сервер**.
Знайомство з інструментами відлагодження API, поки він працює.

## 2. Теоретична база для підготовки

До захисту роботи студент повинен розуміти такі поняття:

- Клієнт і сервер: запит → відповідь. Клієнт — це не «людина»,
  а будь-хто, хто надіслав запит: браузер, мобільний застосунок,
  скрипт, `curl`, інший сервер.
- **Ресурс** та URL, **HTTP-методи** як дієслова над ресурсом
  (GET — прочитати, POST — створити, PUT — змінити, DELETE —
  видалити), **коди відповіді** (200, 201, 404, 400…).
- **REST** як стиль організації API навколо ресурсів.
- **Statelessness** (без стану): кожен запит самодостатній, сервер
  не пам'ятає вас між запитами, поки ви самі не пред'явите
  ідентифікатор (кука/токен — згадайте сесії з ЛР3).
- Формат даних: чому сьогодні у вебі як формат обміну переважає
  **JSON** (легкий, читабельний, нативний для браузера) — той самий,
  що ви бачили у ЛР4.

### Перед виконанням: від ЛР3 до фреймворку

У [ЛР3](/c/networks/labs/lab-03-http) ви написали HTTP-сервер
**руками**: парсили `\r\n`, ліпили відповідь байтами. Це було
корисно, щоб зрозуміти, *що всередині*. Але у реальності так ніхто
не пише — беруть **веб-фреймворк**, який весь цей рутинний розбір
HTTP робить за вас, а ви описуєте лише логіку: «на такий-то URL
з таким-то методом — ось така відповідь». Ця робота — про те, що
будують поверх голого HTTP.

## 3. Завдання на лабораторну роботу

### Завдання 1. Простий REST-API

Реалізувати веб-сервіс (будь-яким веб-фреймворком), який керує
колекцією ресурсів — наприклад, списком нотаток або задач. Мінімум
чотири операції над ресурсом:

- `GET /notes` — повернути список усіх нотаток (JSON);
- `GET /notes/<id>` — повернути одну нотатку; якщо її немає —
  відповісти кодом **404**;
- `POST /notes` — створити нову нотатку з тіла запиту, відповісти
  кодом **201**;
- `DELETE /notes/<id>` — видалити нотатку.

Дані можна тримати просто в пам'яті (звичайний список чи словник) —
база тут не мета. Формат тіла та відповідей — **JSON**.

### Завдання 2. Три різні клієнти до одного сервера

Постукайте по своєму API **трьома різними клієнтами** і переконайтеся,
що серверу байдуже, хто саме прийшов:

1. `curl` з термінала (усі чотири методи);
2. браузер (хоча б `GET`, відкривши URL);
3. невелика програма-клієнт вашою мовою (наприклад, HTTP-бібліотека),
   яка створює нотатку і одразу читає її назад.

### Завдання 3. Хто прийшов? (клієнт очима сервера)

Додайте на сервері логування кожного запиту: виводьте в консоль
**метод, шлях, IP клієнта та заголовок `User-Agent`**. Постукайте
знову всіма трьома клієнтами і подивіться, як сервер їх розрізняє
(`curl`, браузер і ваша програма представляться по-різному). Зробіть
висновок: «клієнт» — це технічна роль, а не людина.

Тут же переконайтеся у **statelessness**: зробіть два однакові
запити поспіль і побачте, що сервер обробляє другий так само, як
перший, — він вас не «запам'ятав».

### Завдання 4. Відлагодження працюючого API

API — це не програма, яку запустив і забув; поки він крутиться, його
треба вміти інспектувати. Ознайомтеся з інструментами (застосувати
щонайменше **два** на вибір, решту — знати, що існують):

- **curl** — базовий інструмент з термінала, ви вже його
  використали;
- **Postman** або **Bruno** — графічні клієнти: зручно збирати
  колекції запитів, дивитися заголовки й тіла, тестувати вручну;
- **Swagger / OpenAPI** — автоматично згенерована сторінка
  документації, де ваш API можна «потикати» прямо з браузера
  (деякі фреймворки дають її з коробки);
- **DevTools браузера** (вкладка Network) — побачити реальні запити,
  які шле сторінка.

### Завдання 5. Автоматичні тести (на додатковий бал)

Ручна перевірка кожного разу — це довго й ненадійно. Напишіть
**автоматичні тести**, які самі шлють запити до вашого API
і перевіряють відповіді: що `GET` неіснуючої нотатки дає 404, що
після `POST` вона з'являється у списку, що `DELETE` її прибирає.
У Python для цього є фреймворк **pytest** (у парі з HTTP-бібліотекою
для запитів). Це перший крок до того, як API тестують у реальних
командах — не руками, а кодом, що ганяється на кожну зміну.

## 4. Вимоги до виконання

- Мова програмування та веб-фреймворк обираються студентом
  самостійно.
- Формат обміну — **JSON**.
- API має коректно повертати **коди відповіді** (не лише 200:
  щонайменше 201 на створення і 404 на відсутній ресурс).
- Завдання 1–4 обов'язкові; Завдання 5 (автотести) — на додатковий
  бал.

## 5. Примітки та підказки

Якщо ви пишете на Python:

- Найпростіший старт — мікрофреймворк **Flask**: кілька рядків, і в'ю
  на маршрут готове (`@app.route("/notes", methods=["GET", "POST"])`).
  Є й сучасніша альтернатива — **FastAPI**: сам віддає JSON
  і генерує Swagger-сторінку автоматично, але тягне за собою async
  і трохи більше нового синтаксису.
- Клієнт-програма (Завдання 2) і тести (Завдання 5) зручно робити
  бібліотекою `requests` або вбудованим `http.client`.
- **pytest**: тестова функція — це звичайна функція з іменем на
  `test_...`, усередині якої ви робите запит і перевіряєте результат
  через `assert response.status_code == 404`. Запуск — командою
  `pytest` у папці з тестами.
- Логи запитів (Завдання 3): у Flask поточний запит доступний через
  об'єкт `request` — там і `request.method`, і `request.path`,
  і `request.remote_addr`, і `request.headers`.
